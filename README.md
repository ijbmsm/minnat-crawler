# minnat-crawler

민낯(술자리) 정치 기록 플랫폼의 수집·분석 파이프라인.
뉴스·법안·팩트체크·판결을 모아 분류하고, 같은 사건끼리 묶어 Supabase 에 넣는다.

프론트엔드는 별도 레포(`ijbmsm/minnat`). 프로젝트 철학과 카테고리 체계는
`minnat/CLAUDE.md`, 운영 현황은 `minnat/STATUS.md` 가 기준이다.

---

## 파이프라인

```
0. 정치인 DB 동기화        sync_politicians.py
1. 다중 소스 수집          crawlers/  (RSS · 네이버 · 국회 API · 팩트체크 · 판결)
2. AI 분류                 analyzer.py      → Claude Haiku 4.5
3. 임베딩 생성             event_matcher.py → OpenAI text-embedding-3-small
4. 사건 매칭 (4단계)       룰 → 임베딩 → LLM → 룰 단독
5. 신뢰도 게이트           trust_gate.py
6. DB 저장 + 사건 생성/머지 db.py, event_manager.py
7. 미검증 사건 자동 승격   auto_verify.py
8. 비활성화 + 스냅샷       scorer.py
```

실행: `python main.py` / 스케줄: `.github/workflows/crawl.yml` (`0 */3 * * *`, 8회/일)
테스트: `python -m pytest tests/ -q`

## 외부 의존 — 크레딧 2개가 따로 필요하다

둘은 **용도도 다르고 지갑도 다르다.** 하나가 떨어져도 파이프라인은 계속 돈다.

| 키 | 쓰는 곳 | 없으면 |
|---|---|---|
| `ANTHROPIC_API_KEY` | `analyzer.py` — 분류·요약·camp 판정 | 분석이 전부 실패 → 저장 0건. 실행이 `exit 1` 로 끝난다 |
| `OPENAI_API_KEY` | `event_matcher.py` — 임베딩 **전용** | 임베딩이 NULL 로 저장 → 유사 사례 빈 목록, Stage 2 매칭 정지. 전량 실패면 `exit 1` |

> OpenAI 는 **임베딩에만** 쓴다. 기사 분류·요약은 Anthropic 이다.
> 그래서 OpenAI 크레딧이 떨어져도 크롤링·분류는 정상으로 보인다 — 실제로 그렇게 몇 달을 돌았다.

그 외: `SUPABASE_URL` / `SUPABASE_SERVICE_KEY`, `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET`,
`ASSEMBLY_API_KEY`, `DATA_GO_KR_API_KEY`. 로컬은 `.env`, CI 는 GitHub secrets.

## 비용 설계

- 기사 1건 = LLM 1회. 소스별 호출 예산을 `main.py` 상단에 상수로 박아
  비용이 소스 개수에 끌려다니지 않게 한다 (RSS 60 / 네이버 30 / 법안 20 / 팩트체크 20).
- URL 사전 중복 제거로 두 번째 실행부터 실제 호출이 예산보다 훨씬 적다.
- 시스템 프롬프트에 prompt caching 을 건다. 캐시 최소 요건(2048 토큰) 때문에
  프롬프트를 **일부러 길게** 유지한다 — "작게" 가 목표가 아니다.
- 매 실행 마지막 줄에 `[비용] 호출 N회 … 추정 $X` 를 찍는다.
  **지금까지의 비용 수치는 전부 추정이다.** 크레딧 충전 후 1회 실행해 실측할 것.

## 조용한 실패를 없애는 규칙

이 레포에서 가장 비싼 교훈은 **"초록색으로 끝나는 실패"** 였다.
2026년 7월 하순 Anthropic 크레딧이 떨어졌는데 예외를 `try/except` 가 삼켜
워크플로가 몇 달간 success 로 끝났다. 같은 일이 OpenAI 쪽에서도 벌어졌다.

그래서 아래를 지킨다.

1. **실패를 대체값으로 덮지 않는다.** 특히 임베딩 실패에 영벡터(`[0.0]*1536`)를 돌려주면 안 된다.
   영벡터는 pgvector 의 `<=>` 가 NaN 을 내고, Postgres 는 NaN 을 **최댓값**으로 취급해서
   유사도 임계값을 통과하고 정렬 1위로 올라온다. 즉 "유사 사례" 가 조용히 무작위가 된다.
   실패하면 `None` → NULL 로 저장한다. 비어 있는 편이 가짜 값보다 안전하다.
2. **집계해서 끝에 드러낸다.** 수집 0건 소스, 임베딩 실패, 버려진 이유를 요약 출력한다.
3. **치명적이면 `exit 1`.** 전 소스 수집 0건 / 저장 0건 / 저장분 전량 임베딩 없음 → 워크플로를 실패시킨다.

## 요약 작성 규칙 (analyzer.py)

뉴스 요약은 **역피라미드**다. 기승전결(소설·에세이 구조)로 쓰지 않는다.

```
순서    가장 중요한 사실 → 배경·이유 → 세부 → 영향
담을 것 무엇(What) · 누가(Who) · 왜(Why) · 영향(Impact)
        언제·어디서는 그 자체가 쟁점일 때만
분량    2~5문장. 길이를 채우려고 늘리지 않는다
```

기사에 없는 내용은 채워 넣지 않는다. 지어내는 것보다 짧은 게 낫다.
단정·평가 표현 금지는 `expression_filter.py` 가 한 번 더 거른다.

### 예정 일정 (`next_branch`)

날짜가 확정된 일정만 뽑아 `issue_clusters.next_branch` 에 넣는다 (프론트가 "다음 분기점" 으로 그린다).
`sanitize_next_branch()` 가 추측성 표현("전망"·"예상"·"조만간"), 과거 날짜, 400일 초과 미래를 버린다.
의심스러우면 버리는 쪽이다 — 추측이 화면까지 새면 서비스 원칙을 정면으로 어긴다.
